# 0010: Field fixes of 2026-11-26: DeepSeek at rung 2 by host, complete reviews, no polling

Date: 2026-11-26. Status: accepted by the owner in the Orca chat of 2026-11-26, after reviewing the findings of a field session in the cockpit64 repository; the owner approved every change below. Implemented in one pull request, in the manner of the 2026-11-18 field fixes (crew64 0.9.0).

## Intent

The owner built this harness to save tokens by sending implementation to DeepSeek. The field session of 2026-11-26 showed that the saving does not happen in a repository where nearly every task is risky tier: the ladder sends every rung 2 implementer to the top Claude model, and risky tier is always rung 2. The same session found five further defects: an orchestrator started in the wrong repository, review passes that each found one new blocker, a deploy before review, an orchestrator woken by its own wait timeouts, and a guard that blocked Claude Code's memory. This record fixes them together, with the evidence at the end.

## Goals

- DeepSeek can implement rung 2 work on a host where the owner says so, without weakening anything else about the risky tier.
- A review pass reports everything it can find, and only real blockers cost a correction cycle.
- A correction cycle never also costs a redeploy.
- The orchestrator waits the way the installed Orca guide says: it ends its turn and Orca wakes it.
- The orchestrator can update its Claude Code memory.

## Non-goals

- Changing the risk tiers, the rung of risky work, the reviewer, or the review-cycle allowance.
- Changing the Bash check of the guard, or any guard denial other than the memory files.
- Choosing a rung 2 DeepSeek overlay for any host. Each host's owner opts in by naming one.

## Anti-goals

- A rung 0 model on a risky task (decision 0004). The rung 2 overlay is the strongest on its host, never the rung 0 one.
- A task that failed on DeepSeek at rung 2 going back to DeepSeek.
- A reviewer told to hold findings back, or a security finding demoted to a follow-up.
- A memory allowance that `$HOME` or a symlink could point into a repository.

## Constraints

- Python 3.13+ and bash on Linux, standard library only, `python3 -I`.
- Every edit is risky tier under docs/05: delegation policy, AGENTS.md, the guard.
- Decision 0004 says the ladder table changes only through a decision record that cites spend and outcome numbers from at least one review period. Change 2 below alters the table without such numbers. It does so by an explicit owner decision, because `features.metering` is `none` and no such numbers exist yet: token counts are self-reported, and one worker reported `unknown`. The first ladder review is to check this change.

## Decision

### 1. The orchestrator session runs in the repository it changes

The orchestrator session runs in a workspace of the repository its tasks change. When the owner's request names a repository other than the one the status line's config path belongs to, the orchestrator says so in its first message and asks the owner to start the session in that repository; read-only work on the other repository may continue. From another repository's workspace the guard blocks the session's writes, the session cannot move into task worktrees or commit a DeepSeek worker's diff, and `--parent-worktree active` resolves to the wrong repository. Written in the orchestrator skill beside the first-command rule.

### 2. DeepSeek at rung 2, opt-in per host

- The DeepSeek row applies at rung 2 only where the host entry's `dsh_profiles` has a non-empty `"2"` name. Without it, rung 2 implementation goes to the Claude row, as before. The shipped defaults and `config/examples/orca-solvela.json` do not set `"2"`.
- The `"2"` overlay must be the strongest DeepSeek overlay on that host, never the rung 0 one. Decision 0004's anti-goal stands.
- Nothing else about the risky tier changes: rung 2, delegated, attended, the Codex reviewer at `--effort high`, the full record.
- A rung 2 task that ran on the DeepSeek row and escalates (a HALT on a stop condition, failed verification, or a reviewer finding marked `blocker` under section 3) is re-dispatched at rung 2 on the Claude row with a fresh worker, and never goes back to the DeepSeek row. It draws on `limits.review_cycles` like any escalation.
- The plan is still written by a rung 2 Claude worker.
- `tools/crew64_config.py` does not restrict `dsh_profiles` keys, so the reader needed no change; `tools/test-crew64-config.sh` now checks that a `"2"` key validates and that the example sets none.

### 3. Reviews: all findings in one pass, re-reviews scoped to the fix

- A first review brief tells the reviewer to report every finding it can find in this pass; the review is complete, not incremental. Each finding is marked `blocker` or `follow-up`. A blocker is wrong behaviour reachable on the Runtime floor with input the system can actually receive, or a security finding. Everything else is a follow-up.
- Only blockers start a correction cycle. Follow-ups are recorded on the pull request, or as issues, and do not draw on `limits.review_cycles`. The same holds for escalation: a reviewer finding escalates a task only when it is marked `blocker`; this replaces decision 0004's "correctness finding" trigger.
- A re-review brief names the earlier blockers and the fix commit range. It asks two questions: is each earlier blocker closed, and did the fix introduce a regression. A new finding outside the fix range is a follow-up, unless it is a security finding or can lose money or data; then it is a blocker, and the correction brief for it says why.

### 4. Order: review, deploy, live check, merge

When a task needs a live check on a server, the order is: implement, review until clean, deploy the reviewed head once, run the live check, then merge. A branch is not deployed before its review is clean. A live check that fails is a correction cycle: it draws on the allowance, and the fix gets a re-review scoped as in section 3. AGENTS.md already put deploy after a clean review; it now names the live check too.

### 5. No polling while waiting

After `worker-start` the orchestrator ends its turn, and acts on each worker message when Orca delivers it. `worker-read` and `inbox` remain the ways to read a result. The `check --wait --timeout-ms 900000` instruction and the `check --ack` instruction are removed. Where the installed guide and the skill disagree on a command, the installed guide wins.

Verified on the local host on 2026-11-26. `orca --version` printed `1.4.271`. `orca skills get orchestration` says:

> Then **end your turn**. "Report back" and "tell me when it's done" still mean end your turn; Orca wakes you and you report then.

> Never:
>
> - Poll or run watch scripts: a script's plain `check` takes your mail, so it is hidden from you and Orca has nothing to wake you with. Orca wakes you.

> In a chat, each message arrives whole as its own message: act on it.

`orca orchestration check --help` says:

> --ack: optional; acknowledges a batch from an older Orca that does not mark it.

> A consuming check marks the batch it returns as handled, so the next check returns newer mail; no --ack is needed.

### 6. The guard allows Claude Code memory files

`tools/hooks/orchestrator-guard.py` allows Edit, Write, MultiEdit and NotebookEdit, from the main checkout and from a worktree, when the target is a memory file:

- an absolute path with no `..` segment;
- both the unresolved normalized path and the real path lie under `<home>/.claude/projects/<one directory>/memory/`, the file at any depth below `memory/`;
- `<home>` comes from the password database for the process's uid, not from `$HOME`, so the environment cannot steer it;
- neither path is inside a repository or a git admin dir (`inside_repository`);
- any error while checking denies.

Memory files are not repository content, so the denial protected nothing. Bash is unchanged. The unit test injects a home through a parameter of `memory_target` that the hook never sets.

### 7. Small text fixes

- `models.orchestrator` shipped default: `claude-fable-5-1` becomes `claude-fable-5-2`, the owner's choice on 2026-11-26; Orca now launches that model.
- The orchestrator skill says that the "Agent roles (Orca)" section of the owner's global `~/.claude/CLAUDE.md` is the default for repositories without crew64, and that in a crew64 repository the skill and docs/05 decide the vendor and the dispatch commands.

## Consequences

- On a host that names a `"2"` overlay, risky work can run on DeepSeek; a failure there costs one escalation to the Claude row from the same allowance. Hosts that name none behave as before.
- Reviews may report more follow-ups per pass and fewer passes per task. Follow-ups accumulate on pull requests and need a home outside the correction cycle.
- A task with a live check deploys once per clean review instead of once per cycle.
- An orchestrator no longer wakes on its own timeouts. If Orca fails to deliver a message, nothing wakes the session; the owner, or `orca orchestration inbox`, is the fallback.
- Reverting is one commit per section: each is text in the plugin, plus one guard function and its tests.
