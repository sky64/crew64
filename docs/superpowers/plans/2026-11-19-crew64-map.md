# crew64-map Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Written for the owner's approval together with the Owner items below; tasks then dispatch without further approval. Rules: `docs/05-delegation.md`, "Model ladder", "Process ladder" and "Plans and owner items".

**Goal:** An Orca sidebar panel that shows the focused repository's crew64 plan live, one row per task, with crew64's numbers, for local and home-office workspaces.

**Architecture:** `tools/crew64_ledger.py` appends one JSON line per orchestrator step to a log outside the repository and mirrors the effective settings into `repo.json`; the orchestrator skill calls it at each step. The Orca plugin `orca/crew64-map/` has a trusted TypeScript worker that reads the log (locally, or on the remote host through whatever Task 1 finds), adds Orca live state and GitHub PR state, folds it into a view model, and a components panel that only displays it.

**Tech Stack:** Python 3.13+ and bash (tool, tests); TypeScript, Orca plugin host API 1.4.255+ (`worker-panel` template, `orca plugin test/check/shot`); `orca` CLI and `gh` called from the worker.

**Spec:** `docs/superpowers/specs/2026-11-19-crew64-map-design.md`

## Global Constraints

- Show only: the panel never stops, dispatches, approves or edits; it only opens links and switches the plan or repository being viewed.
- `features.build_map` (existing, default off) gates log writing; `crew64_ledger.py record` exits 0 without writing when it is off.
- `tools/crew64_config.py` stays the single reader of `.claude/crew64.json`; the plugin reads only `repo.json`.
- Log location: `$CREW64_STATE_DIR`, else `$XDG_STATE_HOME/crew64`, else `~/.local/state/crew64`; repository directory `<main checkout basename>-<first 12 hex of sha256(realpath)>`; one `<plan basename>.jsonl` per plan.
- Event line: `{"v":1,"ts":"<UTC ISO 8601>","plan":"<repo-relative plan path>","task":<int>,"event":"<name>", ...fields}`; events `planned`, `dispatched`, `native_started`, `review`, `escalated`, `committed`, `pr_opened`, `merged`, `abandoned`.
- States and colours: waiting grey, working blue, blocked red, in review amber, done green, abandoned grey struck through, unknown grey `?`. Inferred values carry `~`, unknown values `—`.
- GitHub at most once a minute and only while the panel is open; Orca CLI snapshot on panel open, on `workspace.*` events, and at most once a minute.
- No owner-specific host, bot, path or account in shipped code or defaults (decision 0005).
- Runtime floor for every brief: Python 3.13+, bash on Linux, Orca 1.4.255+.
- Rungs are set here and only climb; a risky-tier task is rung 2; the Tooling table is identical at every rung.

## Review Focus

1. A log with a truncated or non-JSON last line (crash mid-write, disk full): the panel and `show` skip that line and report it once, never blank the plan. → Task 2 test `malformed_lines_skipped`, Task 4 test `foldIgnoresBadLines`.
2. Two orchestrators logging to the same plan at once: lines stay whole. → Task 2 test `concurrent_appends_whole_lines`.
3. A worker's terminal gone (Orca restarted, worker killed) while the log still says dispatched: shown `unknown`, never `working`. → Task 4 test `deadTerminalIsUnknown`.
4. `gh` missing or not logged in: PR cells `?` with one explanation, everything else still renders. → Task 5 test `ghUnavailableMarksPrUnknown`.
5. Focused workspace ambiguous (two repos on branch `main`): picker offered, no wrong repo shown silently. → Task 5 test `ambiguousFocusOffersPicker`.

### Task 2: The ledger tool
